# Manju One：模型与同类应用研究，以及本轮落地

核验日期：2026-09-06。研究对象是用户提供的 R1 产品包，而不是空白新项目。

## 结论

**保留 Manju 的本地、确定性、可恢复制作底座；把进步最快的模型放在可替换的外部工具层。当前最值得投入的是“不丢稿、第一次就能用、交出去不会传错素材、返回后不会覆盖旧成品”，不是把所有新模型接到项目里。**

本轮已把这一判断落实为创作保存保护、空白混音/包装可用性修复，以及有完整性校验的素材上传对照表。没有把官方产品宣传当作个人实测，没有添加付费调用、内部 LLM 或新平台依赖。

### H3 最容易被忽略的具体差异

核验时官方 V2 创建文档列出：H3 为 4–15 秒、768P/2K，支持参考生成；H3-Max 为 5–15 秒、480P/768P，不支持参考图/视频/音频模式，也不支持 2K。首尾帧与参考生成的互斥关系是请求模式约束，不是一个可通过提示词解决的小限制。[S11]

因此，本轮**没有**把“官方已发布”改写为“Manju 已完成原生接入”。目前 `portable_video` / `minimax_h3` 仍为作者交接配置，使用其输出前必须检查目标工具的实际入口；未来原生适配应使用新的、明确版本的执行契约，并单独验证费用、重试、下载和返回素材归属。老包必须仍按创建时的契约解释。

## 二、本轮已经交付的改变

### 1. 从空项目开始的混音与包装

之前“新增”需要克隆一条已经存在的行，因此没有任何音效或信息卡时，恰好无法创建第一条。删除最后一条后也会进入相同死路。

现在行模板由原有 Python 渲染器生成，以浏览器原生 inert template 保存，新增时获得干净默认值。没有从上一行继承文字、样式选择或试听地址，也没有为两个页面重新做一套状态系统。

### 2. 创作保存不再把旧窗口当作最新真相

创作框携带展示文本的版本，保存进入原有跨进程锁、版本比较和原子写入路径。另一窗口或外部助手先保存时，旧窗口收到冲突，而不是覆盖磁盘新稿。未完成的故事草稿不强制通过工程模型校验。

浏览器只把“请求发出时提交的文本”标为已保存。请求过程中继续写的文字仍是未保存草稿；延迟刷新时检查所有阶段，包括被隐藏的编辑器。接口为保持旧客户端兼容，未提供版本的历史调用仍维持旧约定；不能声称所有第三方写入天然免冲突。

### 3. 外部素材包不再只对机器可读

新 `ASSET_MAP.md` 列出首帧、尾帧、其它关键帧、实际文件名与相对路径；另外保留每条主体/控制范围绑定。外链未打包会明确标为 `NOT_PACKAGED`，不会静默下载，也不会假装素材齐全。

此文件来自同一冻结快照，其字节纳入包的语义身份。只篡改上传说明再重算普通文件校验和，不能继续沿用旧交接身份。它仍不证明素材来源许可、模型身份、生成质量或用户批准。

渲染器升到 `2026-09-06.r1`；历史 `2026-08-08.r1` 与 `.r2` 保持可验证。没有更新旧交接包、旧媒体或旧配置限制。

真实合成素材回收还暴露出一个中文用户会遇到的缺陷：纯中文文件名清理后变成 `png` 而不是保留 `.png`，过长英文文件名也会截掉扩展名。现在分别处理安全文件主名与扩展名，在长度上限内保留原来的扩展名；旧渲染器和旧包不被原地改名。这一项有先失败后通过的回归用例，并在真实 PNG 打包中复验。

## 三、下一阶段只需要三道实证，不需要再扩平台

**第一道：真实 Windows 上完成个人操作闭环。** 从开始菜单启动，创建/打开项目、保存第一稿、切页、退出重开，再做更新与回滚。此次容器不能替代 pythonw、COM 快捷方式和 Windows 文件锁实测。

**第二道：用一个可控镜头核验具体生成入口。** 先记录创作意图、模式、参考槽位和返回文件，再判断镜头效果；有明确费用授权后才进行真实生成。此轮未支出费用，也未使用用户额度。

**第三道：同一提交的完整双平台门。** 在依赖齐备、固定 FFmpeg 6.1.1 的环境中完成 Ubuntu 与 Windows 测试。容器里的可用范围回归、合成媒体和浏览器组合测试都只能补充证据，不能替代这一道门。

不需要复制 Flow、Firefly 或 Codex 的全部功能。对个人项目，稳定交接、可逆修改和真实验收的价值高于再出现一排未经实测的模型按钮。
